# Sheldon Go design

## Goal

Build a Go implementation of Sheldon with behaviorally equivalent CLI, configuration, plugin installation, lock handling, and Bash/Zsh source generation. Output does not need to be byte-for-byte identical to Rust Sheldon, but users should be able to use the same commands, config concepts, paths, and environment variables.

## Compatibility contract

The binary is named `sheldon` and exposes these commands:

- `init`
- `add`
- `edit`
- `remove`
- `lock`
- `source`
- `completions`
- `version`

Global options include `--quiet`, `--non-interactive`, `--verbose`, `--color`, `--config-dir`, `--data-dir`, `--config-file`, and `--profile`. The matching `SHELDON_*` environment variables are supported. Default paths follow Sheldon: `$XDG_CONFIG_HOME/sheldon/plugins.toml` or `~/.config/sheldon/plugins.toml`, and `$XDG_DATA_HOME/sheldon` or `~/.local/share/sheldon`.

The TOML model supports shell selection, global matches, global apply templates, custom templates, and named plugins. Plugins support Git, GitHub, Gist, remote, local, and inline sources, plus Git references, protocol, directory, file globs, apply templates, profiles, and hooks.

`lock` installs or validates sources and writes a lock file. `source` re-locks when configuration or installed files are stale, then renders shell code. Bash and Zsh use Sheldon-compatible default matches, apply templates, and source/PATH/path/fpath behavior.

## Architecture

Cobra owns argument parsing and command dispatch. It produces a small runtime context containing resolved paths, profile, shell, and output settings. The command layer calls deep internal modules rather than manipulating TOML, Git, or templates directly.

`internal/config` owns raw TOML decoding, validation, normalization, and minimally destructive config editing. `internal/source` owns Git and HTTP acquisition plus local source validation. `internal/lock` owns source installation, file selection, profile filtering, lock serialization, and lock verification. `internal/render` owns the Sheldon template subset and built-in shell templates.

External side effects are isolated behind small internal adapters. Git uses the installed `git` executable because Sheldon users already need Git semantics and this preserves branch, tag, revision, submodule, and SSH behavior. HTTP uses `net/http`.

## Error behavior

Invalid command-line combinations fail through Cobra. Invalid TOML, multiple source fields, unsupported source options, missing files, failed Git operations, and template errors return contextual errors and a non-zero exit code. `source` writes generated shell code to stdout and keeps diagnostics on stderr so `eval "$(sheldon source)"` remains usable.

## Testing

Tests cover command parsing, default and overridden paths, TOML round trips, add/remove preservation, source normalization, profile filtering, local and inline plugins, glob selection, built-in templates, custom template rendering, lock verification, and end-to-end `source` output using temporary directories. Network-dependent behavior uses local Git repositories and an `httptest.Server`.

## Scope decisions

The first version targets Bash and Zsh behavior. Completion output is generated by Cobra for its supported shells rather than copied byte-for-byte from Sheldon. Lock files use equivalent TOML data and semantics, without requiring identical field ordering or formatting. No GUI, daemon, shell hook installer, or package-manager integration is included.
